Preuve de concept Simulia / LaBotBox · branche poc/simulia-plugin-hotreload · CRLG 2026

Recharger le code robot dans Simulia sans tout recompiler.

Aujourd'hui, changer une ligne de stratégie relink l'intégralité de Simulia — plus de 90 % de code inchangé à chaque itération. Ce POC isole la logique robot dans une bibliothèque dynamique rechargeable à chaud. Voici ce qu'un spike a tranché, l'architecture qui en découle — et la preuve qu'elle tourne.

Stratégie 1 — écartée → Stratégie 2 — implémentée & prouvée

Le problème

Un exécutable monolithique

Simulia.pro (TEMPLATE = app) compile la totalité du code stratégie et machines à états du robot — Modelia, CppRobLib, CM7 — dans le même binaire que toute l'infrastructure Qt. La moindre modification côté Soft_STM32 force à recompiler et relinker tout Simulia.

L'objectif du POC : sortir la logique robot dans un plugin librobotlogic_*.so horodaté, chargé au démarrage et rechargeable à chaud (avec reset de la simulation) — pour itérer sur la stratégie en quelques secondes au lieu d'un build complet.

Contrainte cardinale

La chaîne de compilation et flash du firmware STM32 réel (les Makefile) doit rester totalement intacte. Rien de ce POC ne touche Soft_STM32/.

Le spike

Cinq tests jetables, un verdict net

Avant d'écrire la moindre ligne de production, un mini-projet (exécutable + .so chargé par QLibrary) a reproduit le mécanisme sur la toolchain réelle — Qt 5.15, g++ 11. La question : un exécutable peut-il appeler du code d'un .so rechargeable, et voir la nouvelle version après reload ?

#TestRésultat
A Chargement unique — dlopen + RTLD_GLOBALL'exe appelle une méthode du .so et lit une donnée définie côté exe. Passe
B QLibrary — 2 cycles, même .soChargement, résolution, unload/reload sur le binaire identique. Passe
C Swap v1 → v2 — .so différent, comportement changéAprès reload, la méthode renvoie encore le comportement de la v1. Échoue
D Virtuel vs non-virtuel sous RTLD_GLOBALMême le dispatch virtuel reste collé à la v1. Échoue
E RTLD_LOCAL + interface virtuelle IRobotLogic*Objet créé dans le .so, factory re-résolue à chaque load. Hot-reload réel

Diagnostic

Pourquoi la voie « simple » ne peut pas marcher

La Stratégie 1 gardait le code appelant inchangé grâce à une macro (#define Application (*g_pApplication)) et des symboles globaux. Élégant sur le papier — mais le spike montre que le mécanisme même qui permet à l'exe d'appeler le plugin en direct est celui qui interdit le reload.

Strat. 1 Symboles globaux

Sous RTLD_GLOBAL, la v1 occupe le namespace global. unload() ne libère rien — l'exe y reste lié. Au reload, la factory de la v2 reconstruit un objet avec le constructeur et la vtable de la v1 (interposition de symboles).

v2.step() → renvoie le résultat v1. Le code ne change jamais.

Strat. 2 Isolation + pointeur

Sous RTLD_LOCAL, chaque .so est isolé et unload() libère vraiment. L'exe ne référence aucun symbole du plugin : il ne tient qu'un IRobotLogic* re-obtenu à chaque load. Le dispatch virtuel suit le nouvel objet.

v1.step() → 101 · v2.step() → 110. Reload prouvé.

Architecture retenue

Une frontière unique, tenue par pointeur

Le shell Simulia (CSimulia, l'IHM) devient un dispatcher : il charge le plugin, tient un IRobotLogic*, et ne parle à la logique robot qu'à travers cette interface. Toute la logique — les 15 sous-systèmes agrégés par CGlobaleSimule, la stratégie Modelia, le tick multi-cadences — vit dans le plugin.

Shell · exécutable Qt

CSimulia + IHM

  • Pilote l'interface graphique
  • Charge le .so (RTLD_LOCAL)
  • Lit le DataManager pour l'affichage
  • Reste compilé une fois pour toutes
Plugin · librobotlogic_*.so

CRobotLogic → CGlobaleSimule

  • Les 15 sous-systèmes + Modelia
  • Le tick simu_task_sequencer
  • Publie ses sorties au DataManager
  • Recompilé et rechargé à chaud
shell— IRobotLogic* —▸plugin | ◂— DataManager —

Les cinq principes

  • Isolation. QLibrary en RTLD_LOCAL, jamais ExportExternalSymbolsHint.
  • Interface = données + comportement virtuel. On échange des scalaires, tableaux et pointeurs de structs partagées ; le dispatch est virtuel (vtable de l'objet neuf).
  • Le Qt reste dans le shell. Le plugin ne connaît aucun widget.
  • Le DataManager est le bus de sortie. Le plugin publie, le shell lit pour l'IHM — supprime la plupart des accès directs.
  • Le tick descend dans le plugin. L'ordonnanceur multi-cadences et ses compteurs statiques se réinitialisent naturellement au reload.

Preuve runtime

Le hot-reload tourne dans le vrai Simulia

Plus qu'un plan : le POC est codé, compilé et exécuté. Simulia lancé en mode headless charge une version v1 de la logique robot ; une v2 recompilée est déposée à chaud ; le rechargement est déclenché. Le journal ci-dessous montre le nouveau code s'exécuter, sans redémarrage ni plantage.

Simulia — sortie console 
[CRobotLogic] build marker: V1-BASE              // v1 construite au démarrage
[POC hot-reload] logique robot chargee: …214002.so
[POC hot-reload] auto-reload programmé dans 6000 ms
[CRobotLogic] build marker: V2-RELOADED          // le NOUVEAU code s'exécute
[POC hot-reload] logique robot chargee: …232541.so
[POC hot-reload] logique robot rechargee a chaud: …232541.so

Trois jalons validés par compilation réelle

  • Plugin — librobotlogic_*.so compile et se lie (74 objets, factory ABI C exportée).
  • Shell — Simulia compile et se lie en dispatcher (binaire 5,1 Mo, symboles exportés pour le plugin).
  • Runtime — chargement au démarrage + rechargement à chaud d'une version recompilée, sans crash.

Firmware

Le STM32 n'est pas touché — par construction

Il existe deux fichiers CGlobale.h distincts, un par chaîne de build. Le code partagé de CppRobLib résout #include "CGlobale.h" vers le bon selon son chemin d'inclusion. La transformation du POC n'est écrite que côté Simulia.

Build Simulia · qmake

PluginModules/Simulia/CGlobale.h

  • class CGlobaleSimule
  • Modifié par le POC
Build Firmware · Makefile

CM7/Includes/CGlobale.h

  • class CGlobale
  • Jamais modifié

Règle POC gravée : ne jamais modifier Soft_STM32/CM7/Includes/CGlobale.h ni les Makefile de Soft_STM32. Compilation et flash du robot réel : inchangés.

Coût

Le prix de la robustesse

La Stratégie 2 déplace les dizaines d'accès Application.xxx de CSimulia vers le plugin, derrière l'interface — ils ne disparaissent pas, ils changent de côté de la frontière. Le seul vrai inconnu reste le découplage Qt du lidar simulé.

Amincir CSimulia en dispatcher1–1,5 jmoyen

Pour mémoire, la Stratégie 1 était estimée à ≈ 3–4 j — mais elle ne fournit pas le hot-reload. Le surcoût est le prix, démontré, de la robustesse.

Décision

Ce qui revient au club

La question technique est tranchée et le code existe : le POC fonctionne, sur la branche poc/simulia-plugin-hotreload. Reste une décision d'équipe — adopte-t-on cette base pour toute l'équipe ?

Adopter

Finaliser & fusionner

Base fonctionnelle et prouvée. Reste le polissage : combobox de sélection, découplage Qt complet du lidar, non-régression sur un match. Gain d'itération immédiat pour toute l'équipe.

Archiver

Garder en réserve

Si le gain de temps ne justifie pas d'entretenir cette architecture. La branche reste disponible mais n'est pas fusionnée — aucune trace sur master.

Quoi qu'il arrive, le POC vit dans une branche dédiée : master n'est jamais pollué. C'est tout l'intérêt d'une preuve de concept — aller au bout pour décider en connaissance de cause.

Tester le POC

Cloner, compiler, recharger

Le POC vit sur la branche poc/simulia-plugin-hotreload des deux dépôts. Pré-requis : la toolchain habituelle (Robuntu / Linux, Qt 5.15, qmake, g++). Les dossiers de build sont volontairement frères de Simulia/ pour que les chemins relatifs vers Soft_STM32 résolvent.

1 · Cloner (avec les sous-modules)
# parent + Simulia(LABOTBOX) + CppRobLib, tous positionnés sur le commit POC
git clone --recurse-submodules -b poc/simulia-plugin-hotreload \
    https://github.com/CRLG/GROSBOT_STM32.git
cd GROSBOT_STM32
2 · Compiler le plugin, puis le shell
# plugin -> librobotlogic_<horodatage>.so
mkdir build_plugin && cd build_plugin
qmake ../Simulia/RobotLogicPlugin.pro && make -j$(nproc)
cd ..
# shell Simulia (dispatcher)
mkdir build_poc && cd build_poc
qmake ../Simulia/Simulia.pro && make -j$(nproc)
3 · Lancer & recharger à chaud
# déposer la lib dans le répertoire scanné (défaut : le dossier courant)
cp ../build_plugin/librobotlogic_*.so ./
./Simulia
# puis, dans Simulia : barre d'outils « Logique robot » -> Rafraîchir -> Recharger
# (le combo liste les librobotlogic_*.so ; le clic droit « Recharger » marche aussi)

# — variante headless / CI (sans écran) : reload automatique gaté par variable d'env —
QT_QPA_PLATFORM=offscreen SIMULIA_POC_AUTORELOAD=6000 ./Simulia

Sélection de la lib : clef EEPROM [Simulia] robot_logic_lib_path (défaut "."). Le shell charge la librobotlogic_*.so la plus récente (tri par horodatage du nom). Pour observer un vrai changement de comportement, modifier la stratégie, recompiler le plugin, puis recharger.

Workflow d'itération

La boucle, une fois Simulia lancé

C'est tout l'intérêt du POC : après le lancement initial, on n'arrête plus jamais Simulia. On pointe une fois robot_logic_lib_path vers le dossier de build du plugin, puis on tourne en boucle — chaque tour ne recompile que la logique robot (quelques secondes), pas les >90 % de code Qt inchangé.

Réglage unique — pointer la simu vers le build du plugin
# EEPROM.ini, section [Simulia] : chemin scanné pour les librobotlogic_*.so
[Simulia]
robot_logic_lib_path=../build_plugin
# (à défaut, le dossier de lancement de Simulia est scanné)
Boucle — étape 1

Éditer la stratégie

  • Modifier le code robot, p. ex. Soft_STM32/CM7/Modelia/… ou …/common-rob/Modelia/sm_evitement.cpp
▼
Boucle — étape 2

Recompiler le plugin seul

cd build_plugin
qmake ../Simulia/RobotLogicPlugin.pro && make -j$(nproc)
# -> nouvelle librobotlogic_<horodatage>.so (quelques secondes)
▼
Boucle — étape 3

Recharger dans Simulia (toujours lancé)

  • Barre d'outils « Logique robot » → Rafraîchir (voit la nouvelle lib) → Recharger
  • Le combo permet aussi de choisir explicitement une version ; le clic droit « Recharger » reste dispo
  • La simu se réinitialise et rejoue avec le nouveau code
↻retour à l'étape 1 — Simulia n'est jamais relancé

Avant Cycle actuel

Éditer → recompiler et relinker tout Simulia (Qt inclus) → relancer l'appli → refaire la mise en situation. Long, à chaque essai.

Avec le POC Cycle court

Éditer → recompiler le seul plugin → clic droit « Recharger ». Simulia reste ouvert. Quelques secondes par tour.
